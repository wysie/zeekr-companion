## Confirmed findings and corrections

| Area | Finding | Correction |
| --- | --- | --- |
| GPU preview | Coalesced callbacks can acquire the same latest buffer and repeat drawing/swapping. | Drain input every callback; suppress only duplicate positive acquired timestamps. Settings, taps and resume call the explicit redraw path and remain effective. Timestamp rollback still processes a new frame; freshness observes source progression, not redraws. |
| Canvas correction | Side/HUD/mirror/settings recompute the unchanged projection grid and solve tile homographies each frame. | Cache by map identity plus an owner revision, lane bounds, divisions and target rectangle. Invalidate on framing/size/mode changes. Generic mutable maps keep recomputing unless they supply a revision. Mesh density, pixels, crop and saved choices are preserved. |
| Recorder | A one-second encoder-teardown wait can expire while a frame still uses a bitmap, Surface or SurfaceTexture that the caller then releases. | Reclaim those dependent resources on the queued encoder task after pending work finishes. Timeout ends the caller wait, not resource ownership; repeated release remains idempotent. |
| Updater | Activity recreation can leave an old worker downloading while another clears/reuses its file. | Process-owned jobs with unique staging paths. Workers clean up only their own files; stale jobs cannot publish/install. Rehash the actual closed file before publishing, retaining existing network size/digest checks. |
| Website | Mobile Escape hides focused navigation; full-size screenshot stays phone-width; small notes/controls. | Return focus to Menu, add Actual size/Fit image with scrollable original pixels, use 12px minimum mobile supporting text and 44px key controls. Preserve the existing visual direction and screenshot provenance. |
| Product truth | Storage prerequisites, HUD speed policy, 009 focus and Chinese automatic-recording/360 restrictions differ from implementation. | Correct the English/Chinese docs and website; add first-recording steps and move Install ahead of development history. Archive dated engineering notes separately; mark old restart advice historical. |

## Blind-spot lag: what is established

Both compatibility Canvas and per-pixel GPU paths consume the same native surround
source and share camera/display resources with recording. Compatibility Canvas may
itself be hardware accelerated; “GPU off” does not mean the whole app or recorder
uses no GPU. Recording also does EGL work before codec submission and uses CPU
for overlays, drain/copy and writer work. Stopping recording appearing smoother
supports contention but does not identify CPU, GPU, buffer queues, camera HAL or
USB as the sole cause.

The changes remove source-proven redundant work; there is no measured real-car
FPS/latency improvement yet. No quality downgrade, hidden FPS reduction, automatic
recording interruption or new rendering preference is introduced.

GPU-route descriptions now include unique/duplicate input counts and maximum
acquisition and render/swap wall times over that pipe's lifetime. Acquisition is
measured around `updateTexImage`/transform/freshness observation; render/swap
includes settings taps and driver/buffer waits. These counters are available in
the existing main-preview diagnostics and quality-comparison pipeline details.
They do not measure exposure-to-display latency, isolate GPU execution, measure
individual composite-camera freshness or establish CPU-route frame pacing.

The next performance investigation should compare the same source and window with
recording on/off and rendering Off/All, retaining camera resolution, FOV and
sampling. Correlate unique source progression, UI frame pacing, acquisition/swap
waits, encoder timings and writer backlog with an Android system trace. Decide
whether shared frame fan-out or prioritising active side output is justified only
after that evidence. Keep factory priority, stale-picture covers and output limits.

## Remaining improvements

1. **On-car performance evidence** is the highest-value next step. The current
   tests prove lifecycle and pixel correctness, not sustained head-unit smoothness.
2. **Release/site synchronization:** the website explicitly links a published
   release. Automating that build-time metadata update would avoid manual drift;
   do not silently advertise unpublished app versions.
3. **Documentation ownership:** current setup/defaults belong in the README,
   changes in trilingual changelogs, detailed rendering/vehicle evidence in dated
   docs. A smaller README is easier to keep accurate than repeated feature history.
4. **Design records:** Impeccable reports a legacy PRODUCT schema and a stale
   generated design sidecar. They do not block these fixes. Its `init`/`document`
   workflows can refresh them separately, preserving confirmed product decisions.
