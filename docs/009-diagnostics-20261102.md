## Prolonged missing picture

The evening snapshot contains a clear access-denial/recovery failure:

| Time, 1 November | Evidence |
| --- | --- |
| 19:18:35 | Android/main display wakes; app process survives and is in the background. |
| 19:18:36–37 | Surround is briefly occupied elsewhere and then reported free. Scheduler still says camera access is unavailable until the main Activity comes forward. Popup reports the recorded `ERROR_CAMERA_DISABLED (3)` error. This same denial state was already present before this wake. |
| 19:19:16 | Recording is requested, but **0/3** sources record: surround, front and rear all wait for foreground camera access. |
| 19:25–19:33 | Multiple indicator popups receive no frames; recording remains logically active but waiting. |
| 19:33:48–49 | Main Activity recreates/comes forward; surround opens and produces frames in about 0.3 s, followed by the dedicated cameras and recording. |

The initial platform reason for denying camera access is not established by our
app logs. The app-side recovery defect is identifiable: the scheduler remembers
an actual denial (`unusableSince`), while the recording coordinator's recovery
test only reads the foreground service's cached `startedWhileVisible` eligibility.
That older eligibility can remain true across sleep. The coordinator also treats
the zero-live-source WAITING state as a logically active recording, so routine
resume returns early. A camera becoming free cannot clear this access denial;
the current scheduler intentionally requires a foreground event.

The correction exposes the scheduler's denial episode to recording recovery and
checks it when recording state is published/resumed/started. If recording remains
wanted, every source is waiting, and the screen is on, it requests the existing
foreground recovery path once per accepted denial episode. Factory-camera/quit
guards and the existing launch throttle remain. Rejected factory/throttle
requests do not consume the episode. An accepted request is not proof Android
displayed the Activity; manual app opening remains a fallback. No bypass of camera
permissions or repeated blind camera-open loop was added.

This incident is not evidence that the outstanding-close risk in upstream #117
caused the outage, nor a confirmed explanation for App Lab disappearance.

## Black picture while adjusting Super mirror

Source tracing reproduces a separate GPU presentation bug. `SideGpuOutput`
replaced its `SideGlRequest` on every crop/window-size change, cancelling the old
generation. Its fresh-picture test then looked only in the new generation, which
had no acquired frame yet. Continuous gestures could keep replacing it before the
UI acquired a matching new frame; lifting the finger allowed it to settle.

The correction keeps a bounded history of **output-frame metadata** across
framing edits on the same pipe, output SurfaceTexture and camera lane. It accepts
only the timestamp actually acquired by the UI. The original camera-source age
still expires after 500 ms; settings redraws never renew it. Lane, output or pipe
changes reset continuity; request cancellation/failure still blocks drawing.
No pixel-buffer history, camera rebuild, source resolution or recording change.
